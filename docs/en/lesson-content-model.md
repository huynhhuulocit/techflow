# Lesson content model

This document defines the contract for rich TechFlow lessons. Phase 1 completes the content and review state; Phase 2 binds an interactive simulation to an exact lesson version.

## Three required learning layers

A new lesson, or a lesson marked complete, must contain:

1. **Quick answer**: a short, direct interview answer that includes the relevant conditions.
2. **Conceptual understanding**: an explanation of the actors, data, states, and mechanism order rather than a repeated definition.
3. **Production trade-offs**: benefits, costs, failure modes, and selection conditions for a real system.

`appliedExample` and `misconceptions` support these layers: an example must clarify the mechanism, and a misconception must include a false claim with a concrete correction. Neither replaces production trade-offs.

The Phase 1 contract keeps `shortAnswer` as the quick layer and places the remaining material in optional `LessonContent`:

| Field | Responsibility |
| --- | --- |
| `scope` | Bounds the product, version, or context so a specific flow is not presented as a universal rule. |
| `mentalModel` | Summarizes how the parts relate before presenting detailed steps. |
| `conceptualExplanation` | Explains the mechanism and relationships between actors and states. |
| `actors` | Defines actors with stable IDs, labels, and explicit responsibilities. |
| `mechanism` | Orders steps, references a valid `actorId`, and explains what happens. |
| `productionTradeOffs` | Gives each trade-off a title, benefit, cost, and decision rule. |
| `appliedExample` | Provides one concrete flow with a label, summary, and steps. |
| `misconceptions` | Stores `claim`/`correction` pairs. |
| `evidence` | Lists sources that directly support the technical claims. |

A rich `Lesson` uses lesson-level `reviewStatus` as its technical-review discriminant: `draft-needs-review` has no `review`, while `review` metadata is required for the `reviewed` state. `shortAnswer` is not duplicated inside `content`, but it remains part of the whole-lesson review hash.

## Migration compatibility

Rich content is optional in the shared `Lesson` schema so legacy lessons continue to render during migration. Optional is a compatibility boundary, not a publishing standard:

- a legacy lesson may continue to use `shortAnswer`, `workflow`, and `followUps`;
- the renderer displays rich sections only when their data exists;
- a new lesson must not treat a generic overview or empty workflow as complete content;
- missing rich content must remain visibly incomplete and must not be implicitly treated as reviewed.

Do not create a topic-specific schema or component. Every lesson uses the shared contract in `src/content/types.ts`.

## Evidence and review

Technical claims written manually, imported, or generated by AI need an evidence/review pass before they are considered verified. Evidence stays with the rich content so readers can trace claims; review metadata must bind to the exact content version and include:

- a review status;
- reviewer and review timestamp;
- evidence entries with labels and URLs;
- a content hash that detects changes after review.

The `reviewed` state is valid only while this metadata is complete and `review.contentHash` matches the canonical hash of the complete claim-bearing lesson. `lessonContentHash` covers the title, quick answer, taxonomy, rich content, workflow, and follow-ups; the validator excludes review metadata, progress, and featured state. A content change makes prebuild validation fail until the lesson is reviewed again. AI output always starts as needs-review; attaching an evidence URL does not make generated output verified.

Prefer official documentation or source code for the version being described. Clearly distinguish evidence-backed facts, applied examples, and author inference.

## Vietnamese and English parity

Vietnamese is the default content. Both locales use the same `slug` and must preserve structural parity:

- the same rich-content blocks and the same trade-off/misconception order;
- the same applied-example and follow-up intent, plus the same evidence scope;
- no silent fallback to the other locale when a block is missing;
- technical review and translation review remain separate checks. A rich English lesson uses `translationStatus`, `translatedFromHash`, and `translationReview`; a stale source hash or reviewed translation change fails validation.

The text does not need to be a word-for-word translation, but neither locale may add or remove technical claims. Keep technical terms in English when translation would reduce precision.

## Phase 2: lesson-bound simulation

A rich lesson can attach a schema-v2 `LessonSimulationSpec`. It shares the deterministic playback model used by Question Studio while using source and provenance metadata appropriate for a lesson:

- `source.kind = lesson`, `source.slug`, and `source.contentHash` bind the simulation to an exact narrative lesson version;
- `provenance` distinguishes authored content from AI-generated content instead of making manual content impersonate an AI output;
- `stateFields` provides localized labels and descriptions for machine state keys;
- the validator still strictly checks scenarios, full state snapshots, transitions, and invariants; a failure scenario's terminal state must violate at least one invariant so machine state proves the failure;
- simulation `status` and `review` have an independent lifecycle and never promote the lesson to `reviewed`.

`lessonContentHash` deliberately excludes `simulation` to prevent a circular hash. The validator compares `simulation.source.contentHash` with the current narrative hash; changing the title, quick answer, rich content, or follow-ups makes the simulation stale and the UI fails closed. The simulation review hash covers its source binding, state metadata, playback content, and provenance.

Question Studio keeps the question-bound schema v1 so existing saved drafts remain compatible and explicitly rejects schema v2 at its validation/storage boundary. PWA Kit is the first schema-v2 lesson, with three deterministic scenarios: a cache miss through SSR/hydration/Add to Cart, a cache hit, and a failure caused by reusing personalized output through a shared cache. VI and EN must preserve actor IDs, scenario/transition topology, machine snapshots, and invariant semantics.

Phase 3 adds AI Simulation Studio for rich lessons without changing the publication boundary. The server receives the exact claim-bearing lesson source, independently verifies its source hash, and returns only a schema-v2 `generated-needs-review` draft. A preview can be applied as a local browser override or exported as JSON; neither action edits the lesson registry or creates review metadata. A stale local draft remains available for recovery but cannot run in the player.

Playback uses four learning states for each actor: `waiting`, `active`, `visited` after participation when the actor will return, and `complete` only after that actor's final transition. At a terminal frame, an actor that never appeared is presented as not involved rather than completed. Reduced motion disables autoplay but keeps Step/Back controls; state descriptions must retain readable contrast.

A simulation only visualizes claims already present in the rich lesson. It must not execute markup, mark itself verified, or turn a tenant-specific caching/personalization policy into a universal rule.

## Authoring and merge checklist

- All three learning layers are topic-specific and contain no placeholders.
- Every misconception has a correction; the applied example explains a concrete flow.
- Trade-offs cover both benefits and costs/failure modes.
- VI/EN use the same `slug`, structure, and claim scope.
- Evidence directly supports the important technical claims.
- A lesson simulation matches its source slug/hash, locale, and bilingual machine topology.
- Review metadata appears only after a real review is complete.
- Legacy lessons still render without errors during migration.
- Run `npm run content:check`, `npm run content:validate`, `npm run lessons:validate`, `npm test`, `npm run lint`, `npm run build`, and `npm run test:browser` before merging. `npm run build` runs lesson validation through its prebuild hook; the browser smoke check uses isolated Vite port `4173` and exercises desktop/mobile lesson navigation.
